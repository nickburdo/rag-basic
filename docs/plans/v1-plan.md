# v1 — Инкрементальная индексация базы знаний

**Статус:** утверждён 2026-11-24
**Ветка:** `feature/incremental-indexing` (от `main`)
**Исполнитель реализации:** автор проекта (вручную)

## Цель

Заменить ручной запуск индексации (раскомментирование строки в `src/index.ts`) на отдельную команду `npm run index`. Команда пересчитывает эмбеддинги только для изменённых чанков и удаляет из БД чанки удалённых документов. Индексация запускается автоматически локальными git-хуками при изменении базы знаний в ветке `main`.

## Вне рамок v1

- CI на удалённом сервере (GitHub Actions и т. п.).
- Upload API, админка, хранение документов в БД или S3.
- Атомарность индексации (см. решение D3).
- Автоматическое обнаружение смены модели эмбеддингов (см. решение D4).
- Хук `post-rewrite` (rebase, amend).
- Разграничение доступа к документам в чате.

## Шаги

### Блок A. Разделение базы знаний и проектной документации

- **A1.** Создать папку `knowledge-base/` в корне проекта.
- **A2.** Перенести в неё все документы корпуса чата из `docs/`: `code-review.md`, `deploy.md`, `on-call.md`, `onboarding.md`, `remote-work.md`, `sick-leave.md`, `vacation.md`.
- **A3.** Изменить источник документов для индексации: вместо `docs/` читать `knowledge-base/`.
- **A4.** Убедиться, что в `docs/` остаётся только проектная документация (включая `docs/plans/`) и она не попадает в индекс.

### Блок B. Индексация через LangChain Indexing API

- **B1.** Добавить в индексатор реестр LangChain (Record Manager), который хранится в той же БД Postgres.
- **B2.** Обеспечить создание таблицы реестра, если её ещё нет.
- **B3.** Заменить текущую логику «удалить чанки файла → добавить заново» на вызов `index()` из LangChain.
- **B4.** Использовать режим очистки `full` (решение D2).
- **B5.** Использовать имя файла документа (`source` в метаданных) как идентификатор источника.
- **B6.** После прогона выводить в консоль итог: сколько чанков добавлено, обновлено, пропущено, удалено.
- **B7.** Добавить возможность принудительной переиндексации всех документов: очистить таблицу чанков и таблицу реестра, затем выполнить полный прогон (решения D4, D8). Механизм `forceUpdate` из LangChain не использовать.
- **B8.** Корректно закрывать соединения с БД (vector store и реестр) по завершении, в том числе при ошибке.
- **B9.** При ошибке завершать процесс с ненулевым кодом выхода и понятным сообщением.

### Блок C. Отдельная команда запуска

- **C1.** Создать отдельную точку входа для индексации `src/index-cli.ts`, не связанную с консольным чатом. Логика индексации находится в модуле `src/index-docs.ts` без побочных эффектов при импорте.
- **C2.** Добавить в `package.json` скрипт `index` для обычного запуска.
- **C3.** Обеспечить запуск принудительной переиндексации из командной строки (через тот же скрипт с флагом или отдельным скриптом).
- **C4.** Консольный чат (`npm run dev`, `src/index.ts`) выполняет инкрементальную индексацию рабочей копии `knowledge-base/` перед стартом (решение D9).

### Блок D. Миграция существующих данных

- **D1.** Перед первым запуском нового индексатора однократно очистить таблицу `chunks` от чанков, загруженных без реестра (решение D5).
- **D2.** Выполнить первый полный прогон `npm run index`.
- **D3.** Проверить, что количество чанков в `chunks` совпадает с количеством записей в реестре и что дублей нет.

### Блок E. Проверка инкрементальности (вручную)

- **E1.** Повторный запуск без изменений: все чанки пропущены, ничего не добавлено и не удалено.
- **E2.** Изменение одного документа: пересчитаны только его изменённые чанки.
- **E3.** Добавление нового документа: добавлены только его чанки.
- **E4.** Удаление документа: его чанки удалены из `chunks` и из реестра.
- **E5.** Принудительная переиндексация: все чанки пересчитаны, дублей нет.
- **E6.** Чат (`npm start`) отвечает по документам после переиндексации.

### Блок F. Локальная автоматизация через git-хуки

- **F1.** Создать отслеживаемую в git папку для хуков `.githooks/`.
- **F2.** Хук `post-commit`: запускать индексацию, если текущая ветка `main` и в коммите изменены файлы в `knowledge-base/`.
- **F3.** Хук `post-merge`: запускать индексацию, если текущая ветка `main` и слияние или pull изменило файлы в `knowledge-base/` (включая fast-forward).
- **F4.** Вынести общую логику проверки «ветка + изменения» так, чтобы она не дублировалась между хуками.
- **F5.** При ошибке индексации хук выводит заметное сообщение с подсказкой запустить `npm run index` вручную.
- **F6.** Подключить папку хуков к локальному репозиторию (настройка `core.hooksPath`).
- **F7.** Проверить в рабочей ветке: коммит с изменением в `knowledge-base/` в ветке, отличной от `main`, не запускает индексацию. Тестовый коммит затем убрать. Проверки хуков на `main` выполняются в блоке H (решение D10).

### Блок G. Документация

- **G1.** Создать `docs/indexing.md` и описать в нём:

  - команды обычной и принудительной индексации;

### Блок H. Ревью, слияние в `main` и проверка хуков на `main`

## Журнал решений

| # | Решение | Обоснование |
|---|---|---|
| D1 | Источник правды для документов — git; документы хранятся в `knowledge-base/` | Документы пишут разработчики; история, ревью и права даёт git-хостинг; `docs/` занята проектной документацией |
| D2 | Режим очистки `full` | Каждый прогон читает весь корпус; только `full` удаляет чанки удалённых файлов. Кратковременные дубли во время прогона допустимы |
| D3 | Неатомарность `index()` принимается как известное ограничение | При сбое достаточно повторного прогона; своя атомарность заметно усложнит версию |
| D4 | Смена модели эмбеддингов обрабатывается ручной принудительной переиндексацией | Реестр LangChain не хранит модель; своя таблица учёта для v1 избыточна |
| D5 | Старые чанки удаляются однократно перед первым прогоном | Чанки, загруженные без реестра, `index()` не видит и никогда не удалит |
| D6 | Используется LangChain Indexing API (`index()` + Postgres Record Manager) | Стандартный механизм, полезная практика; проверено по исходникам `@langchain/core` 1.5.0 и `@langchain/community` 1.1.29 — совместим с текущим `PGVectorStore` |
| D7 | CI на удалённом сервере не делается; автоматизация через локальные хуки `post-commit` и `post-merge` | Удалённого репозитория нет; хуки поддерживают индекс актуальным для ветки `main` (уточнено пересмотром 2026-11-25, см. D9) |
| D8 | *Пересмотр 2026-11-24.* Принудительная переиндексация = очистка таблицы чанков и реестра + полный прогон, вместо `forceUpdate` | По исходникам: `index()` с `forceUpdate` повторно вставляет чанки с теми же id, а `PGVectorStore` пишет простым `INSERT` без `ON CONFLICT` в колонку с первичным ключом, поэтому ожидается ошибка дубликата ключа. Запуском не проверялось. Очистка + прогон надёжна и совпадает с процедурой миграции (блок D); пустой индекс на время прогона допустим (локально или в окне обслуживания) |
| D9 | *Пересмотр 2026-11-25.* Консольный чат индексирует рабочую копию `knowledge-base/` при каждом старте. Ошибка индексации не перехватывается: чат не стартует, ошибка выводится в консоль. Веб-сервер (`npm start`) индексацию при старте не выполняет | Без изменений в документах прогон дешёвый (нет вызовов API эмбеддингов). Индексация рабочей копии позволяет проверять ответы чата по черновикам документов до слияния. Консольный чат — инструмент разработчика, перехват ошибки ничего не добавляет к выводу в консоль. Для сервера индексация при старте недопустима: несколько экземпляров запустят параллельный `index()` с конфликтом id; в продакшене индексация — шаг деплоя |
| D10 | *Пересмотр 2026-11-25.* Проверки хуков на `main` перенесены из F7 в отдельный блок H (после документации), вместе с код-ревью и слиянием ветки в `main` | Хуки индексируют только на `main`, а в `main` они появятся только после слияния v1. Слияние ветки само проверяет `post-merge`: ветка меняет `knowledge-base/`. Код-ревью полного диффа перед слиянием согласовано отдельно и теперь входит в план |

## Известные ограничения

- **Хвосты после сбоя.** `index()` пишет пакетами и сразу фиксирует их в реестре, поэтому повторный прогон продолжает с места сбоя. Но очистка в режиме `full` выполняется только в конце: до успешного завершения в БД могут одновременно лежать старые и новые версии чанков.
- **Сбой между записью в чанки и в реестр.** Если процесс упал ровно между записью пакета в таблицу чанков и записью в реестр, повторный прогон может упасть на дубликате ключа. Выход — принудительная переиндексация (B7).
- **Вложенные метаданные не входят в хеш чанка.** LangChain сериализует метаданные через `JSON.stringify(data, Object.keys(data).sort())`. Массив ключей верхнего уровня работает как белый список на всех уровнях вложенности, поэтому вложенные объекты, включая `loc` с номерами строк от сплиттера, хешируются как `{}`. Переиндексацию вызывают только изменения текста чанка и метаданных верхнего уровня (`source`, `title`). Следствие: у пропущенных чанков в БД могут оставаться устаревшие номера строк (`loc`). Сейчас `loc` нигде не используется. Если начнёт использоваться, после изменений структуры документов нужна принудительная переиндексация (B7). Обнаружено при проверке E2 (2026-11-25).
- **Индекс отражает последний прогон.** Хуки индексируют `main`, а консольный чат — рабочую копию. Поэтому после запуска чата на другой ветке или с незакоммиченными правками индекс содержит черновики, пока его не перезапишет следующий прогон.
