# Индексация базы знаний

Как документы из `knowledge-base/` попадают в векторную БД, которой пользуется чат, как запускать индексацию и что делать при сбоях.

## Обзор

```
knowledge-base/*.md ──► загрузка ──► нарезка на чанки ──► LangChain index() ──► Postgres
   (источник правды:                  (500 символов,          │                  ├─ chunks         (чанки + векторы)
    git, ветка main)                   перекрытие 80)         │                  └─ chunk_records  (реестр)
                                                              └─ эмбеддинги считаются только для новых/изменённых чанков
```

- **Источник правды** — Markdown-файлы в `knowledge-base/`, которые хранятся в git. Документы правят через коммиты, а не в БД.
- **Таблица `chunks`** — производные данные для поиска. Её можно в любой момент удалить и пересобрать из `knowledge-base/`.
- **Таблица `chunk_records`** — реестр LangChain (Record Manager, namespace `pgvector/chunks`). В ней одна строка на каждый чанк в `chunks`: хеш чанка (`key`, он же `id` чанка), имя исходного файла (`group_id`) и время последнего прогона, в котором встретился чанк (`updated_at`).
- `docs/` — проектная документация. В индекс она не попадает.

## Где код

| Файл | Назначение |
|---|---|
| `src/prepare-documents.ts` | Загрузка `.md` из `knowledge-base/` (только корень папки) и нарезка на чанки |
| `src/store.ts` | Модель эмбеддингов, векторное хранилище `chunks`, реестр `chunk_records` |
| `src/index-docs.ts` | Логика индексации: функция `indexDocs({ force })`, без побочных эффектов при импорте |
| `src/index-cli.ts` | Точка входа для `npm run index`: разбор флагов, код выхода при ошибке |
| `.githooks/` | Git-хуки для автоматической индексации на `main` |

## Как работает прогон

1. Создаётся таблица реестра, если её нет. Таблица `chunks` создаётся векторным хранилищем.
2. В режиме `--force` обе таблицы очищаются одним `TRUNCATE`.
3. Все документы загружаются и нарезаются на чанки.
4. `index()` обрабатывает чанки пакетами по 100. Для каждого чанка считается хеш (текст + метаданные), и по реестру решается:
   - хеш уже есть — чанк **пропускается**, эмбеддинг не считается;
   - хеша нет — эмбеддинг считается, чанк записывается в `chunks` и в реестр.
5. В конце (режим очистки `full`) из `chunks` и реестра удаляется всё, что не встретилось в этом прогоне: старые версии изменённых чанков и чанки удалённых файлов.

### Итог прогона

```
Indexing complete
Total added records 1
Total updated records 0
Total skipped records 9
Total deleted 1
```

| Счётчик | Значение |
|---|---|
| added | Новые чанки, для которых посчитан эмбеддинг |
| updated | Всегда `0`: механизм `forceUpdate` не используется |
| skipped | Чанки без изменений |
| deleted | Удалённые устаревшие чанки |

Изменённый чанк считается как **added 1 + deleted 1**: в индекс добавляется новая версия, а старая удаляется.

### Что вызывает переиндексацию чанка

| Изменение | Переиндексация |
|---|---|
| Текст чанка | Да |
| Правка на границе двух чанков (в зоне перекрытия 80 символов) | Да, у обоих чанков |
| Заголовок документа (`# ...`), он попадает в `title` каждого чанка | Да, у всех чанков файла |
| Сдвиг строк (например, вставка строки в начало файла) у последующих чанков | Нет (см. «Известные ограничения») |
| Новый файл | Добавляются его чанки |
| Удалённый файл | Его чанки удаляются |

## Команды

Перед запуском должен работать Postgres из `docker-compose.yml`, а в `.env` должны быть заданы `DATABASE_URL`, ключ API и `EMBEDDING_MODEL` (см. `.env.example`).

```powershell
npm run index
```

Обычная (инкрементальная) индексация. Повторный запуск без изменений в документах не вызывает API эмбеддингов.

```powershell
npm run index:force
```

Принудительная переиндексация: очищает `chunks` и `chunk_records` и индексирует всё заново. Можно запустить и так: `npm run index -- --force`.

> ⚠️ `npm run index --force` **без** `--` не работает как ожидается: npm считает `--force` своим флагом, и запускается обычная индексация. Неизвестный флаг, например опечатка `--forse`, приводит к ошибке и коду выхода 1.

```powershell
npm run dev
```

Консольный чат сначала выполняет инкрементальную индексацию **рабочей копии** `knowledge-base/`, затем стартует. Это позволяет проверить ответы чата по черновику документа до коммита. Если индексация упала, чат не стартует, а ошибка выводится в консоль.

Веб-сервер (`npm start`) при старте **не** индексирует. В продакшене индексация должна быть отдельным шагом деплоя: несколько одновременно стартующих экземпляров сервера запустили бы параллельные прогоны с конфликтом id.

При ошибке `npm run index` печатает `Indexing failed: ...` и завершается с кодом 1. Соединения с БД закрываются и при ошибке.

## Когда нужна принудительная переиндексация

Обычный прогон пересчитывает только чанки с изменённым хешем. Принудительная (`npm run index:force`) нужна, когда меняется то, что в хеш не входит, или когда индекс оказался в несогласованном состоянии:

- **смена модели эмбеддингов** (`EMBEDDING_MODEL`) или размерности векторов. Векторы разных моделей несравнимы, а реестр не хранит модель. Без переиндексации поиск будет тихо возвращать нерелевантные чанки;
- **изменение настроек нарезки** (`chunkSize`, `chunkOverlap`, тип сплиттера). Без переиндексации получится, что часть чанков нарезана по-старому, часть по-новому;
- **нужны актуальные номера строк** (`loc`) в метаданных (см. «Известные ограничения»);
- **после сбоя**, если повторный обычный прогон падает на дубликате ключа;
- **после ручного вмешательства** в таблицы `chunks` или `chunk_records`.

На время принудительного прогона индекс пуст, и чат не найдёт документы.

## Git-хуки

Хуки поддерживают индекс актуальным для ветки `main` без ручного запуска.

### Подключение (один раз после клонирования)

```powershell
git config core.hooksPath .githooks
```

Эта настройка хранится в `.git/config` и в репозиторий не попадает. Её нужно выполнить в каждом новом клоне.

### Когда срабатывают

| Хук | Событие | Что сравнивается |
|---|---|---|
| `post-commit` | Каждый коммит, включая завершение слияния с конфликтами | `HEAD~1` и `HEAD` |
| `post-merge` | `git merge` и `git pull`, включая fast-forward | `ORIG_HEAD` и `HEAD` |

Оба хука вызывают `.githooks/reindex-if-changed.sh`. Он запускает `npm run index`, только если:
1. текущая ветка — `main`;
2. в сравниваемом диапазоне изменились файлы в `knowledge-base/`.

В остальных случаях хук молча завершается: коммиты в других ветках и коммиты в `main` без изменений в базе знаний индексацию не запускают. `git reset` хуки не вызывает. `git commit --amend` — это коммит, и для него срабатывает `post-commit`. Поведение при `rebase` не проверялось, хук `post-rewrite` не подключён. После таких операций на `main` надёжнее запустить `npm run index` вручную.

### Если индексация в хуке упала

Коммит или слияние **уже выполнены**, хук не может их отменить. Выводится сообщение:

```
==================================================
 INDEXING FAILED. Run 'npm run index' manually.
==================================================
```

Нужно устранить причину (не запущен Postgres, нет ключа API и т. п.) и запустить `npm run index` вручную.

### Требования к файлам хуков

- **Окончания строк LF.** С CRLF `sh` падает. Это обеспечивает `.gitattributes` (`.githooks/* text eol=lf`).
- **Флаг исполняемости в git** у `post-commit` и `post-merge` (`git update-index --chmod=+x ...`). На Windows не обязателен, на Linux и macOS без него хук не запустится. `reindex-if-changed.sh` вызывается через `sh` и флаг не требует.
- При коммите из WebStorm вывод хука виден в окне **Git → Console**. Ошибка `npm: command not found` означает, что IDE запущена без Node в `PATH`.

### Отладка

Чтобы убедиться, что хук вызывается, и увидеть, какие команды он выполняет:

```sh
GIT_TRACE=1 git commit -am "message" 2>&1 | grep -E "post-commit|post-merge|rev-parse|diff|npm"
```

Строка `run_command: ... .githooks/post-commit` означает, что хук запущен. Дальше по командам скрипта видно, на какой проверке он остановился.

## Известные ограничения

- **Индексация не атомарна.** При сбое посередине прогона в БД может остаться частично обновлённое состояние. `index()` фиксирует в реестре каждый записанный пакет, поэтому повторный `npm run index` продолжает с места сбоя и не пересчитывает уже записанные чанки.
- **Хвосты до успешного завершения.** Очистка устаревших чанков выполняется только в конце прогона. До успешного завершения в индексе могут одновременно находиться старая и новая версии чанков, и чат может найти обе. Исправляется успешным прогоном.
- **Сбой между записью чанка и записью в реестр.** В этом редком случае повторный обычный прогон падает на дубликате ключа. Выход — `npm run index:force`.
- **Вложенные метаданные не входят в хеш.** LangChain хеширует метаданные так, что вложенные объекты (в том числе `loc` с номерами строк) превращаются в `{}`. Сдвиг строк не вызывает переиндексацию, поэтому у пропущенных чанков в БД могут оставаться устаревшие `loc`. Сейчас `loc` не используется.
- **Индекс отражает последний прогон.** Хуки индексируют `main`, а `npm run dev` — рабочую копию. После запуска консольного чата на другой ветке или с незакоммиченными правками в индексе остаются черновики. Чтобы вернуть индекс к `main`, переключитесь на `main` и запустите `npm run index`.
- **Модель эмбеддингов не отслеживается.** При её смене нужна принудительная переиндексация (см. выше).

## Что делать при сбое

1. Прочитать ошибку: обычно это недоступный Postgres, недоступный API эмбеддингов или неверный ключ.
2. Устранить причину и запустить `npm run index`. Прогон продолжит с места сбоя.
3. Если повторный прогон падает на дубликате ключа (`duplicate key value violates unique constraint`), запустить `npm run index:force`.

## Проверка состояния индекса

```sql
-- Chunk and record counts must be equal
SELECT
  (SELECT count(*) FROM chunks)        AS chunks,
  (SELECT count(*) FROM chunk_records) AS records;

-- Chunks without a record in the registry (expect 0 rows)
SELECT c.id
FROM chunks c
LEFT JOIN chunk_records r ON r.key = c.id::text
WHERE r.key IS NULL;

-- Chunks per source file
SELECT group_id, count(*) FROM chunk_records GROUP BY group_id ORDER BY group_id;
```
